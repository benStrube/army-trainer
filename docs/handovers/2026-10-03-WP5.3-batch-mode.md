## Done
- ✅ `src/army_trainer/batch.py` and CLI commands, recorded as **D16** in `docs/PROJECT_SCOPE.md`:
  - `army-trainer batch <list> [--stages ...] [--force] [--target N] [--inbox DIR]`
  - `army-trainer check-updates [<list>] [--inbox DIR]`
  - `army-trainer build <ID> [--pdf PATH]` (was a stub; now the same pipeline for one publication)
- ✅ **Batch rules:**
  - The list has one `ID [path-or-URL]` per line; IDs may contain spaces ("FM 3-09"). With no source, the PDF comes from `data/inbox/<ID>.pdf` or `data/raw/`.
  - Every PDF goes through `fetch.fetch` (the gate). The gate files (`fetch/gate.py`, `llm_guard.py`) are untouched. A rejected publication is never converted, and one failure never stops the rest.
  - Up-to-date stages are skipped (`--force` redoes them); a changed PDF is re-fetched and re-converted.
  - **No committed spec, or a spec planned from another PDF revision, means "needs planning":** the batch writes the planning packet and stops. It never writes a spec. `render` and `qa` run only where a current spec exists.
  - Results print as a table and are saved to `data/batch/report.json`. Exit code 1 if any publication was rejected, had no input, or failed ("needs planning" is not an error).
- ✅ **`check-updates`** is read-only for `data/raw`. It takes a candidate (list entry, `data/inbox/<ID>.pdf`, or the URL the PDF was fetched from), gates it in a temp folder, and reports unchanged / changed (newer, older, or same date) / rejected / unreachable / no source. It flags a committed spec that would need re-planning. Downloads are still limited to `armypubs.army.mil`.
- ✅ 23 new tests in `tests/test_batch.py` (list parsing, 5 synthetic publications through convert and index, rejection and no-input isolation, skip/force, needs-planning, stale spec, every check-updates status, CLI). 168 tests pass; ruff clean.
- ✅ Real run on the FM 3-09 data: `batch` gives `ok` (38 slides, qa 0 errors); an unfetched `AR-600-20` gives `no_input` with the instruction.
